# 竖屏与动感：现状与下一步

> 这一篇是**决策记录**：已落地到哪一步、为什么停在这里、下一步从哪里接。
> 写下来的目的不是催办，而是让下一次有人动手时不必重新考古。

## 一、竖屏（9:16）：**已能出片，但仍是 experimental**

### 已经做完的（三步走里的第一步与半步）

| 项 | 状态 |
|---|---|
| 画布/安全区单一真源 | ✅ `scripts/layoutkit.py`：`LANDSCAPE` / `PORTRAIT` 两份 profile，filmkit 从这里取常量 |
| 选择机制 | ✅ `VIDEO_STUDIO_LAYOUT` 环境变量（在 `import scenes` 之前定死）+ `render.py --layout portrait` |
| 安全区与字幕带 | ✅ 竖屏 SAFE `(65,120,1015,1610)`、SUB_BAND `(80,1450,1000,1616)`——字幕整体上移，避开系统 UI 区 |
| 字号 | ✅ `scenes._TYPE_SCALE = W/1920`：竖屏 0.5625，横屏恒 1.0 |
| 版式几何 | 🟡 `scenes._fit_layout`：把 `ST.LAYOUTS` 的 x/y/宽按画布比例折算（不是重排） |
| 文字不出画 | ✅ `scenes._fit_px`：唯一的绘制入口把文本左边界钳进 SAFE，并记录 `_CLAMPED` |
| 自检 | ✅ 第 75 条：竖屏画布真的是 1080x1920、10 类构图全部出图、过宽文字必被钳住 |

### 为什么还没到"可交付"

**版式是折算来的，不是为竖屏设计的。** 具体表现：

* 内容整体偏上、下半屏大片留白（横屏的 y 常量按 1080 高设计，折算到 1920 高只用了上半部分）。
* `left-stack` 在竖屏仍是左文右卡——两侧都被压到 400px 左右，而竖屏更该是**上下**结构。
* `compare` 的左右对照在竖屏应改上下对照；`list` 应纵向堆叠而不是两列。

这些是**版式重设计**，不是调个系数。折算能让它"能看、不崩、字不出画"，但到不了"好看"。

所以 `render.py --layout portrait` 会打印一段 warn，`selfcheck` 也只守底线不守观感。

### 下一步（按顺序，每步都可独立验收）

1. **竖屏原生版式**：给 `ST.LAYOUTS` 加竖屏变体（`left-stack@portrait` 等），而不是折算。
   `list` 改单列纵向、`compare` 改上下、`process` 改竖向流程轴。
2. **新录金帧**：`golden_frames.py` 的基线要按 profile 分开存，不能共用一个文件。
3. **重算断言阈值**：`selfcheck` 第 68/72 条断言的是**像素位移台阶**（2 灰阶），竖屏下要重算。
4. **`filmcheck` 放行**：`VIDEO_OUT_ALLOWED` 是白名单，要加入竖屏宽高对。
5. **`estimate.py` 基准**：1080p 的帧率不能直接套到 1080x1920（像素数相同但构图更密）。

## 二、动感（亚像素推镜）：**仍未做，但结论没变**

1.2.0 关掉的是**抖动**，不是**运动**：`push` 0.04 在 8 秒走 7px ≈ 0.03px/帧，`int(round())`
取整后变成"每几帧整块跳 1px"（实测 0.02 → 0.67 次/秒，0.14 → 4.4~12 次/秒）。
修法是 `_view()` 恒返回 `_View(1.0)`、默认 `push = 0.0`——问题消失，动感也消失。

正确的解不是关掉缓推，而是**消掉取整**：

* **超采样下采样**（推荐）：2× 分辨率渲染再 lanczos 缩回。0.03px/帧 在 2× 空间是 0.06px/帧，
  取整台阶被平均掉；代价是单帧像素 ×4。`filmkit` 里已用过这个论证（1920→1280 下采样 = 1.5× 超采样）。
* **亚像素仿射**：`PIL.Image.transform` 浮点平移，成本小得多，但**所有**图层（文字/装饰/安全区遮罩）
  必须走同一条路径，否则会出现"底版在动、文字不动"的错位——比抖更糟。

### 验收判据（别用"看起来顺了"验收）

* 复用第 72 条：`push = 0` 时缩放恒 1.0、标题带连续 30 帧逐字节一致。
* 新增反过来的：`push = 0.04` 时相邻帧位移**单调**（无回退）且**单帧位移 < 0.5px**。
* 只在显式开关下启用；默认仍走 1.0 缩放，保证既有金帧与全部既有断言不动。

## 三、为什么这两条要和别的改动分开

1.3.0 / 1.4.0 改的是上下文成本、CI 覆盖、依赖上界、单真源、审美质检——全部可以做到
**默认渲染零变化**，验收口径是既有断言一条不改地全绿（金帧逐像素一致）。
竖屏与动感恰好相反：**必然**改像素与版式，必然要新录金帧。混在一个提交里，出问题时
分不清是"我又把哪里弄坏了"还是"新功能的预期变化"。

所以 1.5.0 的处理是：把竖屏的**基础设施**做完并守住底线（能出片、字不出画、有自检），
把**版式重设计**留成明确的下一次——而不是假装它已经适配好了。
