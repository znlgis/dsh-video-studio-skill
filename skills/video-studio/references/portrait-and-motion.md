# 竖屏与动感：两条**有意推迟**的路线

> 这一篇不是功能说明，是**决策记录**：两条被推迟的路线、为什么会推、动手时改哪里、
> 以及验收标准。写下来的目的不是催办，而是让下一次有人想改的时候不必重新考古。

## 一、竖屏（9:16）：该做，但不该“把宽高换一下”

### 现状（为什么现在是 fail-closed）

`filmkit.video_plan` 对非 16:9 直接抛错，理由写在代码里：安全区、版式几何、HUD、
字幕折行**全部按 1920×1080 的像素坐标写死**。竖屏不是缩一下就能出片——
16:9 里“左文右图”的构图搬到 1080×1920 会变成上下两条细带；字幕带（`SUB_BAND`）
在竖屏里应该更靠上（避开系统 UI 与评论区）；`layout_cycle` 的版式轮换也要重新设计。

好消息是耦合比想象中少：`assets/scenes.py` 里**没有**任何 1920/1080 硬编码，
`filmkit.py` 只有 4 处。真正写死坐标的是 10 类构图绘制器内部的比例常量。

### 动手时的路径（按顺序，每步都可独立验收）

1. **先抽 `LayoutProfile`，行为零变化**。把画布尺寸、安全区、字幕带、HUD 边距收进
   `profile(width, height)`，默认值**精确等于**今天的常量。这一步的正确验收是：
   `selfcheck` 72 条全绿、`golden_frames --check` 逐像素一致（一个字节都不能变）。
2. **再加竖屏 profile**，只让几何自己流出来（安全区 = 8% 边距、字幕带上移、
   字号按短边换算而不是按高度）。此时**必须**新录一版金帧，并新增一条断言：
   “竖屏下所有上屏文本仍在安全区内”（`preflight` 已有逐字字形检测，复用即可）。
3. **最后才重排构图**。`hero / list / stat / compare / process / quote / chapter / chart / outro`
   在竖屏里是**不同的版式**，不是同一版式的缩放：列表在竖屏更适合纵向堆叠，
   `compare` 左右对照要改上下对照。这一步会动 `designkit` 的 `layout_cycle` 与 `scenes.py`。

### 会被打破的既有契约（提前知道，别改到一半才发现）

| 契约 | 影响 |
|---|---|
| `golden_frames.json` | 新增 profile 后基线要按“每 profile 一套”分开存，不能共用一个文件 |
| `selfcheck` 第 68/72 条（缩放稳定性 / 前景锁定） | 断言的是**像素位移台阶**，竖屏下要重算阈值而不是照抄 1080p 的 2 灰阶 |
| `filmcheck` 的 `video` 块校验 | `VIDEO_OUT_ALLOWED` 是白名单，竖屏要放行新的宽高对 |
| `estimate.py` 的耗时基准 | 1080p 的帧率不能直接套到 1080×1920（像素数相同，但构图更密） |

## 二、动感（亚像素推镜）：1.2.0 关掉的是**抖动**，不是**运动**

### 现状

1.2.0 的复盘很干净：`push` 0.04 在 8 秒里走 7px ≈ 0.03px/帧，`int(round())` 取整后
变成“每几帧整块跳 1px”，实测 0.02 → 0.67 次/秒、0.14 → 4.4~12 次/秒的跳变。
修法是 `_view()` 恒返回 `_View(1.0)`、默认 `push = 0.0`——**问题消失了，动感也消失了**：
现在段落中段是整帧静止，statement/stat/compare/quote 相邻帧差为 0。

静态预渲染 + 完全不动，长段落会显呆。观众感知到的是“PPT”，不是“镜头”。

### 正确的解：消掉取整，而不是关掉缓推

两条路，都不改渲染频率：

1. **超采样下采样**（推荐）：在 2× 分辨率（3840×2160）下渲染，再用 lanczos 缩到 1080p。
   0.03px/帧在 2× 空间里是 0.06px/帧，取整台阶被平均掉；代价是单帧像素 ×4。
   `filmkit.py` 里已经用过这个论证（1920→1280 的下采样等于 1.5× 超采样），只是没用在推镜上。
2. **亚像素仿射**：底版与前景分别用 `PIL.Image.transform` 做浮点平移，不进整数 paste。
   代价小得多，但要保证**所有**图层（文字、装饰、安全区遮罩）走同一条路径，
   否则会出现“底版在动、文字不动的错位感”——比抖更糟。

### 验收标准（别用“看起来顺了”验收）

- 复用 selfcheck 第 72 条的判据：`push = 0` 时缩放恒 1.0、标题带连续 30 帧逐字节一致；
  新增一条反过来的：`push = 0.04` 时**相邻帧位移单调**（无回退）、且**单帧位移 < 0.5px**。
- 只在 `--supersample`（或 `design.visual.push > 0` 且 profile 允许）时启用；
  默认仍走 1.0 缩放，保证既有金帧与所有既有断言不动。

## 三、为什么这两条没有和其他优化一起做

这一轮（1.3.0）改的是**上下文成本、CI 覆盖、依赖上界、单真源、审美质检**——
全部可以做到“渲染行为零变化”，验收口径是 72 条断言一条不改地全绿。
竖屏与动感恰好相反：它们**必然**改像素与版式，必然要新录金帧、必然要改若干条断言。
把两类改动混在一个提交里，出问题时根本分不清是“我又把哪里弄坏了”还是“新功能的预期变化”。

所以这里的处理是：**方案、影响面、验收标准写清楚，代码留到单独一条分支**。
